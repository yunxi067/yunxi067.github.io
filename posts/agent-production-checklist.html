Agent 工程落地清单

一个 Agent 能演示，不代表它能交付。真正上线前，要回答六个问题：它能做什么，不能做什么，凭什么判断，如何验证，失败怎么办，谁来接管。Demo 证明的是“模型有潜力”，生产证明的是“系统有边界”。

一、先定义任务边界

不要从“做一个智能助手”开始，那太宽。应该从一个明确任务开始：修复测试失败、整理邮件、生成周报、审查代码、查询知识库、操作某个后台系统。任务越具体，Agent 越容易被验证。

边界定义至少包含三项：输入是什么，允许做什么，完成标准是什么。没有完成标准的 Agent 很容易变成“看起来很努力，但不知道是否真的完成”的系统。

任务边界模板

name: code-review-agent
scope:
  can_do:
    - 阅读 PR diff 和关联文件
    - 标出潜在 bug、回归风险、缺失测试
    - 给出最小修改建议
  cannot_do:
    - 直接合并 PR
    - 直接修改生产配置
    - 基于猜测评价未读取的文件
done_when:
  - 每条发现都有文件位置和理由
  - 严重级别可解释
  - 明确说明没有验证到的风险

二、权限必须最小化

Agent 可以调用工具后，权限就是第一风险。能读不代表能写，能写不代表能删除，能调用 API 不代表能操作生产数据。权限应该按任务拆分，而不是按模型能力一次性放开。

  • 读权限和写权限分开。
  • 本地文件、远程仓库、数据库、第三方 API 分开授权。
  • 删除、覆盖、发布、付款、发邮件等动作必须有确认或审批。
  • 所有工具调用都要留下可追踪记录。
工具 默认权限 需要审批的动作
代码仓库 读取文件、查看 diff、运行测试 批量改文件、删除文件、推送分支、合并 PR
Shell 只读查询、构建、测试、格式化 删除、移动目录、修改全局环境、部署发布
数据库 只读查询脱敏数据 写入、删除、DDL、查询敏感字段
外部 API 读取文档、查询状态 发消息、扣费、创建真实订单、触达用户

三、上下文要可信、够用、不过载

Agent 的很多错误不是模型“笨”，而是上下文错了。它读了旧文档、漏了关键配置、把示例当生产规则，都会导致错误决策。

上下文工程要处理三件事：来源可信，版本明确，内容适量。不要把所有东西塞给模型，而是让它按任务检索必要信息，并在关键判断前引用证据。

真实落地时，我会把上下文分成三层：第一层是当前任务必须读取的硬上下文，比如失败日志、PR diff、接口文档；第二层是按需检索的软上下文，比如历史 issue、相关模块说明；第三层是禁止默认相信的背景信息，比如模型训练记忆、过期 Wiki、群聊里的一句口头约定。Agent 每次做关键判断，都应该说明它依据的是哪一层上下文。

上下文类型 常见风险 工程处理
代码文件 只读片段导致误判调用关系 先检索引用点，再读取关键文件
接口文档 版本过期或训练数据不一致 优先查官方文档或项目内签名
历史对话 遗漏用户最新指令 执行前复述当前目标和约束

四、工具调用要可验证

工具调用不是越多越好。一个可交付 Agent 应该知道什么时候用搜索，什么时候读文件，什么时候跑测试，什么时候停止。每个工具调用都应该服务于下一步决策。

关键原则是：高影响操作前必须读上下文，修改后必须验证，失败后必须先定位根因。否则 Agent 会像一个手很快但没有经验的新人，越忙越危险。

工具调用轨迹示例

1. read_test_output
   evidence: OrderCancelServiceTest 第 42 行断言失败
2. search_code("cancel order stock deduction")
   evidence: 找到 OrderCancelService 和 InventoryService
3. read_file(OrderCancelService.java)
   evidence: paid 状态未提前返回
4. apply_patch
   change: 只调整状态校验顺序
5. run_tests("OrderCancelServiceTest")
   result: passed

五、评测要覆盖真实任务

如果 Agent 只在玩具任务上表现好，上线后一定会遇到落差。评测集应该来自真实工作：历史 Bug、真实代码库、常见工单、典型邮件、失败部署、用户经常问的问题。

评测不要只打一个最终分。更有价值的是分层记录：任务是否完成、是否读了正确上下文、是否调用了正确工具、是否产生不必要修改、失败时是否停止、解释是否可信。

一条真实评测记录可以这样落库

{
  "task_id": "eval-2026-05-01-017",
  "task_type": "fix_failing_test",
  "success": true,
  "context_score": 0.92,
  "tool_trace_score": 0.88,
  "unnecessary_changes": 0,
  "verification": "OrderCancelServiceTest passed",
  "human_review": "accepted",
  "cost": {
    "duration_seconds": 214,
    "tool_calls": 9
  }
}
评测维度 应该观察什么 不合格信号
任务完成 目标是否真实达成，是否通过验证 只给解释，没有可验证结果
上下文质量 是否读取了必要文件、文档和历史状态 凭常识猜测项目结构或 API 行为
工具轨迹 工具调用是否必要，顺序是否合理 跳过读取直接修改，失败后反复试错
风险控制 是否识别高风险操作并停下确认 删除、覆盖、发布等操作没有确认

六、监控和人工接管决定能不能长期运行

Agent 上线后，必须观察任务成功率、工具失败率、平均成本、人工接管次数、用户撤销次数、错误类型分布。没有监控，就不知道它是在变好还是在悄悄制造风险。

人工接管不是失败，而是安全设计。需求不明确、权限不足、测试失败、涉及生产数据、操作不可逆时，Agent 应该主动停下，把证据和建议交给人判断。

我会特别关注“看起来成功但人工撤销”的任务。这个指标比单纯失败率更危险，因为它说明 Agent 可能在错误地自信。比如代码能编译、测试也过了，但改动把业务语义做偏了；或者生成的周报格式正确，但结论引用了旧数据。生产化 Agent 必须让这种问题可见。

上线后应该看的指标

  • 任务成功率：最终是否完成，而不是是否生成了回复。
  • 验证通过率：测试、检查、人工抽检通过的比例。
  • 人工接管率：哪些任务经常需要人介入，说明边界或上下文还不够好。
  • 工具失败率：Shell、API、浏览器、检索工具分别在哪里失败。
  • 单位任务成本：每类任务消耗的 token、时间和外部 API 成本。
接管触发器 Agent 应该交给人的内容
需求歧义 已知事实、冲突点、推荐选项和影响
验证失败 失败命令、错误摘要、已经尝试过的修复路径
高风险权限 即将执行的操作、影响范围、回滚方式
成本异常 当前消耗、卡住的位置、是否建议终止

上线前最低清单：任务边界明确；权限最小化；上下文来源可信；工具调用有日志；核心任务有评测集；失败有重试、回滚或人工接管；成本和错误可观测。

七、从 Demo 到生产的推进顺序

不要第一天就让 Agent 接管完整业务流。我更推荐四步走：先做只读分析型 Agent，再开放低风险写操作；先在沙箱仓库跑，再接入真实仓库；先人工审核每次输出，再逐步放开低风险自动化；先看任务级指标，再决定是否扩大场景。

这套节奏看起来慢，但它能让团队知道风险在哪里。Agent 工程不是“赌模型突然变聪明”，而是不断收窄失败空间，把不确定任务变成可管理的工程过程。

结论

Agent 工程化的目标不是让模型显得聪明，而是让它在复杂任务中稳定地产生价值。一个真正可交付的 Agent，必须像工程系统一样被设计、测试、监控和治理。

本文要点

Agent 上线标准不是“能回答”，而是“能在边界内可靠完成任务”。
